# ucrt_xp by katahiromz

## そもそもUCRTとは

C言語の `malloc` や `printf`、`fopen` といった基本機能は、実行時に「CRT(C Runtime Library)」というライブラリが提供しています。

問題は、Visual Studioのバージョンごとに別のCRTが存在することです(`MSVCR71.dll`、`MSVCR90.dll`、`MSVCR100.dll` など)。同じプログラムにVS2005製のDLLとVS2010製のEXEが混在すると、それぞれが別々のCRTを使うため、次のような事故が起きます。

- DLLが `malloc` したメモリをEXE側で `free` するとクラッシュする
- `FILE*` をモジュール間で渡すと壊れる
- ロケールやエラー番号(`errno`)の状態が食い違う

Microsoftはこの問題を解決するため、Windows 10以降に「Universal CRT(UCRT)」を導入しました。どのバージョンのコンパイラでビルドしても、OS標準の**1つの共通ランタイム**を使う仕組みです。ただしUCRTはWindows XPでは動きません。

## ucrt_xp は何をするものか

Windows XP向けに、UCRTと同じ考え方を実現する**自作の共通ランタイム**(`ucrt_xp.dll`)です。MSVC 6〜2010のどれでビルドしたモジュールも、この1つのDLLにリンクすればCRTの食い違いが起きません。README冒頭の「どのMSVCバージョンでコンパイルしても、ABIが安定した1つのランタイムにリンクする」という設計思想がそのままです。現在、C++はサポートしていません。

## 想定されるユースケース

**1. 複数のVCバージョンが混在するレガシー資産の保守**
古いDLL(VC6製)、中間のDLL(VC2005製)、新しいEXE(VC2010製)が混ざったXP向け業務アプリで、メモリ確保・解放やファイルハンドルの受け渡しを安全にします。

**2. 今も動き続けるXP環境向けのソフト開発**
工場の制御PC、医療機器、POS端末、計測機器などは、今もXPで稼働しているものがあります。そこに新しい機能を追加するとき、最新ツールチェーンに依存しない形で共通の土台を用意できます。

**3. プラグイン/SDK提供**
自分のアプリにサードパーティがDLLプラグインを作る場合、相手のコンパイラバージョンが分からなくても、`ucrt_xp.h` の安定したC APIを境界にすれば破綻しません。

**4. 標準CRTの既知の欠陥を避けたい場合**
- `localtime` が共有バッファではなく出力引数で結果を返す(スレッドセーフ)
- `time_t` が64bitで2038年問題がない
- `rand` が常にスレッドごとの状態を持つ
- `errno` がスレッドローカル

**5. XPの古いRTMでも動く互換層として**
`InitOnceExecuteOnce` や `CONDITION_VARIABLE` などVista以降のAPIを、XPでも動くよう代替実装しています。

**6. 学習・研究用途**
「CRTとは何をしているのか」「ABI互換性をどう設計するか」を学ぶ、コンパクトなリファレンス実装としても読めます。

## 導入のしやすさ

- `#define UCRT_XP_IMPLEMENT_AUTOSTART` で初期化を自動化
- `ucrt_xp_compat.h` で `malloc` / `fopen` / `printf` などおなじみの名前のまま使える

## 注意点(READMEにも明記されています)

- **C標準ライブラリの完全な代替ではありません。** `math.h` の三角関数、`setjmp`、`signal.h` などは対象外です。
- **実機での動作は未検証です。** MinGWでコンパイル・リンクが通ることだけ確認済みで、XPやWine上での実行テストはされていません。本番投入前に `tests/test_basic.c` を実機で走らせる必要があります。
- **C++例外のバージョン間互換は解決できません。** `throw` したオブジェクトの内部構造はコンパイラ依存で、これは構造的な限界だとREADMEに書かれています。
- ライセンスはMITです。

一言でまとめると、「バラバラのVisual Studioバージョンで作られたモジュールが、Windows XP上で安全に協調動作するための共通土台」です。
